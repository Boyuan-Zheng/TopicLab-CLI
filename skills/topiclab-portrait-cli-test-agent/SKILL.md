portrait product through `topiclab-cli`.

If you only clone one repository, clone `TopicLab-CLI` and read only this file.

## Official Install Method

For the portrait preview lane, the official installation method is source
clone from GitHub, not npm.

Run exactly:

```bash
git clone --branch preview/portrait https://github.com/Boyuan-Zheng/TopicLab-CLI.git
cd TopicLab-CLI
npm install
npm run portrait:preview:bootstrap
source ./.topiclab-cli-home/portrait-preview.env
```

Then verify the command surface exists:

```bash
node dist/cli.js portrait --help
```

Current pinned preview version in this repo:

- `0.4.0-portrait.2`

## Core Mental Model

The installation is local, but the runtime is cloud-backed.

Local machine owns:

- the cloned repository
- `npm install`
- `npm run build`
- `TOPICLAB_CLI_HOME`
- downloaded artifact files such as PDF or PNG

Cloud staging runtime owns:

- account auth
- portrait sessions
- portrait state
- execution logs
- server-side artifacts

So the test target is not “can one command run locally”.

The real target is:

- can a local CLI keep talking to the cloud portrait runtime over many commands

## Register Or Login Rule

Treat `portrait auth ensure` as the single register-or-login command.

Canonical command:

```bash
node dist/cli.js portrait auth ensure \
  --phone <your_phone> \
  --username <your_username> \
  --password '<your_password>' \
  --json
```

Expected behavior:

- if the account already exists, it logs in
- if the account does not exist, the CLI tries to auto-register first

Important deployment precondition:

- self-registration only works when public staging exposes:
  - `GET /api/v1/auth/register-config`
  - `POST /api/v1/auth/register`
- the current public staging URL has already been re-verified on `2026-04-11`
  and does expose these auth routes

If you receive:

- `404 No route for GET /api/v1/auth/register-config`

that means:

- the CLI code supports register-or-login
- but the current staging deployment has drifted or regressed away from the
  verified setup

In that case, report it as a staging deployment issue, not a CLI usage issue.

## Unified Command Surface

Use only this main loop unless debugging is explicitly requested:

1. `topiclab portrait auth ensure`
2. `topiclab portrait start`
3. `topiclab portrait respond`
4. `topiclab portrait status`
5. `topiclab portrait result`

Session control:

- `topiclab portrait resume`
- `topiclab portrait history`
- `topiclab portrait reset`
- `topiclab portrait export`
- `topiclab portrait artifacts list`
- `topiclab portrait artifacts get`
- `topiclab portrait artifacts download`

Do not default to lower-level debugging commands.

## Default Portrait Loop

After login, do this:

```bash
node dist/cli.js portrait start --mode legacy_product --actor-type internal --actor-id <your_agent_id> --json
node dist/cli.js portrait respond --external-text-file ./ai-memory-reply.md --json
node dist/cli.js portrait status --json
node dist/cli.js portrait respond --text "我是测试智能体 Alpha，目前主要做 AI agent 与科研工具开发。" --json
node dist/cli.js portrait result --json
```

Prompt-first rule:

- after `portrait start --mode legacy_product`, the backend should already
  return the `ai_memory` prompt-first step
- do not ask a human to choose A/B
- do not ask a human to copy the prompt to another AI
- the current CLI-using agent should read the returned prompt and answer it
  itself
- first preference:
  - `portrait respond --external-text-file`
- after the prompt reply is imported, continue following the server-driven next
  step through `portrait respond ...`

## Continuous Use Rule

Do not treat the CLI as a one-shot command.

You should keep using the same local CLI state:

- `TOPICLAB_CLI_HOME`
- or the env file generated by `portrait:preview:bootstrap`

If you pause and later continue:

```bash
source ./.topiclab-cli-home/portrait-preview.env
node dist/cli.js portrait resume --json
node dist/cli.js portrait status --json
```

## Interview-The-Agent Rule

Do not start by asking a human to copy a prompt somewhere else.

Instead:

1. start the portrait session
2. read the returned `AI 记忆提取提示词`
3. answer that prompt as the current agent, based on your own long-term memory
   and accessible context about the user
4. send the full answer back through:
   - `portrait respond --external-text-file ...`
5. only after that continue the follow-up questions returned by the backend

If the first prompt-first answer is still too thin, you may do more rounds of:

- `portrait respond --text ...`
- `portrait respond --external-text ...`

## Input Rule For `respond`

Use exactly one input family per call:

- `--choice`
- `--text` or `--text-file`
- `--external-text` or `--external-text-file`
- `--external-json` or `--external-json-file`
- `--confirm`

Priority order:

1. prompt-first reply:
   - `--external-text-file`
   - or `--external-text`
2. follow-up answers returned by the backend:
   - `--choice`
   - `--text`
3. session control:
   - `status`
   - `result`
   - `resume`
4. structured debug import only when explicitly needed:
   - `--external-json`

## Binary Export Rule

The portrait product is not limited to markdown.

Also validate binary export when requested:

```bash
node dist/cli.js portrait export --kind profile-pdf --json
node dist/cli.js portrait export --kind profile-image --json
node dist/cli.js portrait artifacts list --json
node dist/cli.js portrait artifacts download <artifact_id> --json
```

Interpretation:

- the cloud backend renders the file
- the local CLI downloads the bytes
- the local machine writes the file
- the backend keeps a durable artifact record

Note:

- not every artifact is binary-downloadable
- markdown/text artifacts may exist only as cloud-side structured records
- use `portrait artifacts download <artifact_id>` when the listed artifact has
  `binary_available=true` or a non-empty `download_url`

## Failure Recovery

If something fails, use this order:

1. `404 No route for GET /api/v1/auth/register-config`
   - public staging has regressed and is missing the auth route
   - self-registration cannot work until staging is repaired
2. `404 No route for /api/v1/portrait/...`
   - public staging has regressed and is not exposing the latest portrait backend
3. `Missing portrait auth token`
   - re-run `portrait auth ensure`
4. `Portrait auth expired or is invalid`
   - re-run `portrait auth ensure`
5. `No active portrait session is stored locally`
   - run `portrait resume` or start a new session
6. network error
   - confirm `TOPICLAB_BASE_URL`
   - confirm the staging URL is reachable over HTTPS

Do not work around auth failures by editing `state.json` manually.
Re-run `portrait auth ensure` and report the exact backend error instead.

Always distinguish:

- local install problem
- CLI auth problem
- public staging route exposure problem

Do not merge them into one vague failure.

## Reporting Rule

Your report must say:

1. whether clone, install, and bootstrap succeeded
2. whether register/login succeeded
3. the exact portrait commands you executed
4. whether the interaction stayed continuous across multiple CLI commands
5. whether the runtime was clearly cloud-backed
6. any exact failure and its layer
7. whether prompt-first started automatically and the current agent answered the
   prompt itself
8. whether export/artifact listing worked
9. whether binary artifact download worked, if a downloadable artifact existed
